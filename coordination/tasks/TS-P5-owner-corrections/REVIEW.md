## Verified correctness

- **Exact-key isolation.** The debounce key is built by one shared `debounceKey(triggerType, target, blockId)` used by both `maybeTrigger` (set) and `releaseRepeatSuppression` (remove), so the formats cannot drift. The values round-trip exactly: the engine forms the key from `EventRepository.TARGET_TYPE_APP`/`TARGET_TYPE_SITE` (`"app"`/`"site"`), the matched raw package/domain and `ref.blockId`; `launchBlockScreen` puts those same trigger fields into the intent extras; `releaseDetectionSuppression` reads them back from the loaded session. Package names and domains cannot contain `:`, so the composite key is unambiguous. `releasingDifferentDetectionKeyDoesNotAllowImmediateRetrigger` covers wrong-target and wrong-block isolation; App B independence follows from per-key removal.
- **All no-access outcomes release; nothing else does.** Gate **Not now** (`gateWalkAway`) and active-challenge escape (`escape` → `challengeWalkAway`) both return a `WalkAway` effect whose handler releases before `clearLiveChallenge()` while the session is still loaded. Gate Back (`finish()` → `onStop` GATE branch), active Back (`moveTaskToBack` → `onStop` ACTIVE branch) and screen-off (`backgroundChallenge` for ACTIVE/GATE) also release; screen-off followed by `onStop` can double-release the same key, which is idempotent. Configuration changes (`isChangingConfigurations`) never release. `releaseDetectionSuppression` self-guards to PAUSE purpose with non-null target/triggerType, so turn-off sessions — which begin in Toki and carry no detection key — can never release.
- **Successful completion is preserved.** `beginCompletion` moves to COMMITTING and `commitSucceeded` moves to TERMINAL before `returnToTriggeringApp()`/`finish()`; the subsequent `onStop` sees neither ACTIVE nor GATE and does not release. No `persistCompletion` branch releases: success routes through the unchanged `2543329` return-to-triggering-app path (so a completed user landing back on the app is not immediately re-gated), a failed commit returns the runtime to ACTIVE with the challenge continuing, and the destroyed case is a no-op. Backgrounding during COMMITTING does not release, matching the documented intent that an in-flight or completed challenge keeps loop prevention; residual exposure there is bounded by natural debounce expiry.
- **Duplicate suppression retained.** `maybeTrigger` still records `lastFired[key] = now` on every fire and suppresses repeats inside the window; the release only removes the single exact key on explicit no-access outcomes, so repeat suppression for every other key and moment is unchanged.
- **Coordinator/service lifecycle.** The app is single-process (no `android:process` attributes), so the application-scoped process-local coordinator is valid. `onServiceConnected` detaches any prior engine before attaching the new one; `onDestroy` detaches — identity-checked (`===`), so a stale detach cannot clear a newer engine — and nulls the field. All coordinator and engine entry points are `@Synchronized`; activity lifecycle and accessibility callbacks already serialize on the main thread of the shared process. If the service is unbound at release time the call is a no-op and the next engine starts with empty debounce memory, so the release is already satisfied, as the coordinator KDoc records. Detach-on-destroy bounds the strong engine reference to the service lifetime; no leak.
- **Immediate re-trigger.** After release, the next `TYPE_WINDOW_STATE_CHANGED` for the same package passes `maybeTrigger` immediately even inside the 10-second window (`releasedAppSuppressionAllowsImmediateRetrigger` fires at t=1 ms < 10 s). **Not now** → immediate reopen therefore yields a fresh gate, and Back/background during a live challenge → immediate reopen brings the retained challenge forward through the existing `onNewIntent` guard (ACTIVE/COMMITTING/WALK_AWAY retained; a GATE relaunch re-resolves to an equivalent fresh gate for the same block, which is pre-existing behavior).
