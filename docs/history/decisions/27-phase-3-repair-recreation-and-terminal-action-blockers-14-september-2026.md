## Phase 3 repair — recreation and terminal-action blockers — 14 September 2026

Bounded repair of the two Codex blockers on `9a88b41` (base `6c3b962`; GLM 5.3). Code committed; this record and the handoff checkpoint stay uncommitted with the owner's in-flight documentation edits (R7 precedent).

- **Blocker 1 — restoration.** The route stack is now `rememberSaveable` over a string codec: `ui/navigation/Routes.kt` holds `Route` (plus `Route.Welcome` and `ChecklistMode`, moved out of the checklist file), `RouteCodec.encode/decode` (small `"turnOn:<id>"`-style shapes; garbage decodes to null; an all-null restore falls back to the initial stack), and `RouteStackSaver` (plain `Saver` to `ArrayList<String>` — `listSaver` would not infer on Compose 1.6/Kotlin 1.9.24). Recreation mid-flow now restores checklist mode, block id, explainer/battery position and the welcome screen itself; a saved `launchResolved` flag stops the first-run welcome check from re-pushing Welcome over a restored onboarding stack. Outstanding permission requests live in a saveable `SnapshotStateList<AppPermission>` injected into `PermissionEventLogic`, so a recreation mid-request settles exactly one granted/denied from real system state on the next resume (pinned in tests, including restored-request no-duplicate after callback+resume). The battery picker selection is `rememberSaveable`. Ordinary resume refresh and revoked-permission refresh are unchanged.
- **Request ordering semantics (blocker 1 requirement).** `requestPermission` in MainActivity: mark pending synchronously → durably insert `permission_requested` (suspend) → launch the system UI; a failed insert or a failed launch rolls the pending mark back so no phantom outcome can settle. A successful `permission_requested` row is kept when the subsequent launch fails — the tap was a real request attempt; only the outcome is suppressed. The notifications runtime dialog uses the same helper with its activity-result launcher as the launch step and settles from the callback.
- **Blocker 2 — terminal mutations.** New `ui/util/TerminalAction` runs once-only operations single-flight in the **activity lifecycle scope** (never a destination composable scope): competing taps are ignored synchronously (`busy` also disables Turn it on / Not yet / Continue), `onChanged` (haptic) fires only when the commit reports a real change, `onCommitted` (navigation/refresh) only after success, failures stay on screen with no side effects and release the guard for retry. TurnOnScreen absorbs system Back while its commit is in flight, so Back/Not yet can neither cancel an accepted commit nor produce a second pop. The checklist Continue runs through the same guard; the gate push and Get started are one-shot against the stack.
- **Atomicity at the persistence boundary.** `BlockRepository.setEnabledRecordingTransition(id, enabled)` commits the blocks row and its `block_turned_on/off` event in one `withTransaction` (transition events are written beside the state change — `EventRepository.log` would run outside the transaction; first-launch parity kept). The DAO `setEnabled` gained `AND enabled <> :enabled` and returns the row count, so an already-stored value emits no event (and upstream, no haptic) — repeated OFF after completion is a no-op transition. The bare `setEnabled` is now `internal` (fixture seeding and future internal re-arm only; visible to the test source sets via the friend path). `EventRepository.completeOnboarding(grantedCount)` commits the `onboarding_completed` event and the one-way `onboarding_completed_at` marker in one transaction and at most once (in-transaction marker check); the separate `markOnboardingCompleted` was removed so no write path can create the marker without the event. `EventRepository` now takes the `TokiDatabase` in its constructor (TokiApplication and the two androidTest constructions updated mechanically — no behaviour change).
- **Signature notes.** TurnOnScreen dropped its `eventRepo` parameter (the event now commits inside the repository transaction); BlockListScreen dropped its unused `eventRepo`. MainActivity's `requestPermission` helper is passed into the checklist as `onRequestPermission(permission, launchSystemUi)`, centralising mark/record/launch/rollback for overlay and notifications as well.
- **Intentionally unchanged.** The delete path (Phase 2-reviewed R14 confirm dialog) is not part of either blocker and keeps its existing write pattern; Samsung/generic battery copy, notification-denial UX, haptic strengths and all unrelated UI are untouched; Phase 2 surfaces (CreateFlowScreen, Domain.kt, ownership/nonempty/30-char/multiline-domain logic) show no diff since `9a88b41`.
- **Coverage added (JVM, runBlocking + CompletableDeferred/Unconfined — no new dependencies).** `RouteCodecTest` (4): every route round-trips exactly — onboarding/gate/settings checklist, explainer, battery, TurnOn/Detail ids, Create edit id + step, welcome; damaged input decodes to null. `TerminalActionTest` (5): double-tap single-flight (one commit/haptic/close), effects only after commit completes and while busy the guard is held, failure emits no effects and releases for retry, unchanged value skips the changed-effect, accepted commit survives its caller scope being cancelled. `PermissionEventLogicTest` grew 7 → 13: restored pending settles granted/denied exactly once, restored request cannot duplicate after callback+resume, multiple restored requests each settle once, rollback-unmark prevents outcomes, double-mark yields one outcome.
