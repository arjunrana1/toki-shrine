## Phase 3 implementation — onboarding and permissions — 14 September 2026

Built from approved Phase 2 base `6c3b962` (GLM 5.3, single builder, scope stated per §3c). Screens 1–4 and 24, accessibility-gated activation, activation haptics after success. Code committed; this record and the GLM handoff checkpoint remain uncommitted alongside the owner's in-flight documentation edits (R7 precedent — do not sweep owner content into the builder commit).

- **The accessibility service exists as a Phase 3 prerequisite.** Without a declared service the app cannot appear in Android's accessibility list, so the row could never flip to granted and the gate could never pass. `TokiAccessibilityService` is declared in the manifest (`exported="true"` with the signature-level `BIND_ACCESSIBILITY_SERVICE` permission so only the system can bind) and observes nothing — no events, no URL reading, no `accessibility_connected/disconnected` events; all of that is Phase 4 detection. Config requests `canRetrieveWindowContent` (address-bar reading needs it) but subscribes to no event types.
- **Activation gate, every entry path (PRD §12).** Both ON toggles (home row, detail switch) route through one `openTurnOnOrGate` in MainActivity: accessibility granted → turn-on confirmation; missing → the permission checklist opens instead, nothing enables. The confirmation's *Turn it on* re-checks accessibility before persisting (a revocation while the screen is open enables nothing and opens the checklist), so final confirmation is gated too. Denial paths emit no success haptic.
- **Haptics fire only after success.** `BlockHaptics.turnedOn/turnedOff` moved after `setEnabled` + event write complete in all three call sites (TurnOnScreen, BlockListScreen, BlockDetailScreen) — closes the Codex note that haptics fired before the persistence coroutine. Tuning unchanged (preset heavy click/click), still pending owner feel.
- **Permission state model.** `data/permissions/Permissions` reads real system state per permission: accessibility via our ComponentName in `ENABLED_ACCESSIBILITY_SERVICES`, overlay via `Settings.canDrawOverlays`, battery via `PowerManager.isIgnoringBatteryOptimizations`, notifications via `POST_NOTIFICATIONS` check. A hoisted snapshot in MainActivity refreshes on every activity ON_RESUME, so returning from any system settings screen flips rows without manual refresh; the notification dialog result also refreshes via its activity-result callback.
- **§10 permission events via pure `PermissionEventLogic` (JVM-tested).** `permission_requested` fires when a system UI is actually launched (explainer's *Continue to settings*, battery screen's *Open battery settings*, the Grant pill for overlay/notifications). On resume, each outstanding request settles exactly once as `permission_granted`/`permission_denied` against real state; notifications settle from the dialog callback (no double emission — pinned in tests). `eventValue` strings: accessibility / overlay / battery / notifications. Known limitation: the pending-request set is composition state; if the system kills and recreates the activity mid-request, the outcome event is lost (state still refreshes correctly).
- **Checklist modes and onboarding events.** One checklist component, three entries: ONBOARDING (welcome → Get started, logs `onboarding_started`), GATE (ON toggle without accessibility), SETTINGS (permission-health row). Continue in onboarding mode logs `onboarding_completed` with `granted_count`, writes the one-way `app_meta.onboarding_completed_at` flag, and pops to the block list; in gate/settings mode it just returns (no onboarding events — onboarding_completed means the first-run flow, not a re-visit). Welcome returns on every launch until that flag exists; Back from welcome reveals the block list — never a gate (PRD §12). Permission request/grant/deny events fire in all three modes.
- **Battery screen paths.** `Build.MANUFACTURER` detection (case-insensitive samsung) defaults to Samsung; the "Not a Samsung? Pick your phone" link opens an in-place Dialog picker with exactly two choices — Samsung and "Another manufacturer" (generic). Samsung: the three authored steps and *Open battery settings* → app details screen (where Battery → Unrestricted lives). Generic: no OEM steps; intro copy plus the same CTA firing the universal `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` dialog (manifest gained the normal `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` permission) — this reads "the universal Android battery-optimisation dialog is the baseline path" as the generic-maker path. Generic intro copy is builder-authored pending owner confirmation; OEM text moves into the Phase 4 bundled-JSON loader alongside the browser map. Override is screen-local (re-detected on later visits). *"I've done this"* just returns; state settles on the next resume.
- **Explainer before the system screen (PRD §5).** Accessibility Grant pushes the explainer; its CTA pops the explainer *then* launches system accessibility settings, so returning lands on the checklist with refreshed state. The system-settings description string mirrors the explainer's do/never-do lists.
- **Row copy follows PRD §12, not the mock.** Overlay description reads "Shows the timer bubble" (§12's stated purpose; the mock's "pause screen and the timer bubble" contradicts §13 — the block screen needs no overlay). Accessibility/battery/notifications descriptions match both.
- **Settings (screen 24).** The mock's "Countdown messages — updated remotely" row is removed (PRD §6). Permission health reuses the checklist (GATE-style back); its subtitle is "All 4 granted" / "n of 4 granted", with the outlined check pill only when all four are granted. Supported browsers is inert with subtitle "Chrome, Firefox, Samsung Internet + 6 more" (nine total per §13; mock listed only three) — the browser-map UI is Phase 4. Send feedback is inert (Phase 7). Theme is static "Dark". About row reads "About Toki Shrine" (naming rule) with the real version from PackageManager ("v0.1.0"), replacing the mock's static "v0.1". `settings_viewed` logs on entry.
- **Navigation mechanics.** New routes: Checklist(mode), AccessibilityExplainer, BatteryInstructions, Settings. The welcome screen is an overlay state over the block list rather than a stack route (first-launch decision deferred via a nullable flag so the list never flashes); its Get started pushes Checklist(ONBOARDING). System Back: welcome reveals the list, checklist pops one route, onboarding Continue pops to root.
- **Notifications runtime dialog**: manifest gained `POST_NOTIFICATIONS`. Android's don't-ask-again behaviour after two denials means the Grant pill may return instantly denied — expected platform behaviour; granting then requires app notification settings. Flagged for the owner checklist.
- **Manifest summary after Phase 3:** VIBRATE, POST_NOTIFICATIONS, REQUEST_IGNORE_BATTERY_OPTIMIZATIONS (all normal/install-time) + the picker `<queries>` + the accessibility service declaration. No dangerous permissions beyond POST_NOTIFICATIONS, no new dependencies.
- **Checks run (no device operations):** `./build.sh assembleDebug` green; `testDebugUnitTest` 24 JVM tests green (7 Stats + 5 Domain + 7 PermissionEventLogic + 5 OemBattery — the two new suites pin event sequences and manufacturer selection/override); `assembleDebugAndroidTest` compiles (forced recompile verified); Phase 7 hex-colour grep clean. Instrumented execution, install, and all permission/granting/device behaviour remain pending owner-led validation per §3a. No instrumented UI tests were added for the new screens: the gating logic lives in MainActivity callbacks against real system state, so compiling-only tests would assert little; the pure logic is JVM-covered instead.
