## Phase 0 — Project skeleton and Nocturne theme

- **Toolchain versions (Phase 0).** AGP 8.4.1, Kotlin 1.9.24, Compose compiler 1.5.14, Compose BOM 2024.06.00, activity-compose 1.9.0, core-ktx 1.13.1, lifecycle-runtime-ktx 2.7.0, Room 2.6.1 (runtime + ktx only — no KSP/room-compiler until Phase 1 needs it). Constrained by the committed Gradle 8.7 wrapper and JDK 17; HANDOVER.md warns AGP newer than ~8.4 won't run on Gradle 8.7. AGP 8.4.1 and Kotlin 1.9.24 were also already in the local Gradle cache. **Constrains later phases:** do not bump any of these without re-checking the Gradle 8.7 ceiling.
- **compileSdk 36 on AGP 8.4.1 (Phase 0).** AGP 8.4.1 is only tested up to compileSdk 34, so `android.suppressUnsupportedCompileSdk=36` was added to `gradle.properties` (the property AGP itself suggests) to silence the warning. targetSdk stays 36 per the stack spec. Compiling and packaging work; if a future phase hits an API that behaves differently under the older compiler, revisit this pairing rather than Gradle.
- **CSS px → dp/sp 1:1 (Phase 0).** The design renders at a 400×800 CSS px viewport (`design/regenerate-screens.py`), so one CSS px maps to one dp, and text px to sp. No scaling factor.
- **Inter bundled as a font resource (Phase 0).** The Nocturne type token requires Inter; Android doesn't ship it, so `inter_regular.ttf` (400) and `inter_medium.ttf` (500) live in `res/font/`. The CSS @import also loads 600/700 but no token or component rule uses them — not bundled. Anton stays a Phase 5 asset.
- **Shadow tokens translated as edge + ambient (Phase 0).** Nocturne shadows are a 1px hairline edge plus an offset blur; Compose can't offset blurs, so the translation is: edge colour applied as a border, blur as `Modifier.shadow` with elevation ≈ blur ÷ 2 (md 18px → 9dp, lg 40px → 20dp), and the `rgba(0,0,0,α)` layer carried as `shadowColor` alpha (0.55 / 0.65). Pure black here is the design readme's stated shade exception.
- **Hex in `res/values/colors.xml` (Phase 0).** The launch-window background (`android:windowBackground`) and launcher icon must resolve before any Kotlin runs, so `#161826` and `#9184d9` are duplicated there, commented as mirroring the tokens. The hex-grep acceptance only covers `app/src/main/java`, and these two values are taken from tokens, not invented.
- **Launcher icon (Phase 0).** Minimal adaptive-icon XML only (minSdk 33 > 26, so no bitmaps needed): a torii-gate mark stroked in the accent colour on the bg colour. Placeholder-quality by design; replace when a real mark exists.
- **Material 3 mapping (Phase 0).** Nocturne has no M3 colour scheme, so one was mapped: primary = accent, onPrimary = bg (matches the CSS radio checked state), primaryContainer = accent-800 / onPrimaryContainer = accent-100 (the .tag-accent pair), outline = neutral-700, outlineVariant = divider, onSurfaceVariant = neutral-400, and all `surfaceContainer*` = surface so M3 dialogs read like the CSS `.dialog`. Typography maps h1–h6/body plus the component-layer sizes (14/13/12/11/10) onto M3 slots; shapes map sm/md/lg onto the five M3 slots. Ramps are exposed as `NocturneTheme.colors.*` alongside the M3 scheme.
- **--color-divider alpha (Phase 0).** `color-mix(in srgb, #e9e9ed 16%, transparent)` → `0x29E9E9ED` (16% of 255 ≈ 41 = 0x29).
- **Phase 0 UI scope (Phase 0).** The empty themed screen is literally empty — a full-bleed bg-colour box under `NocturneTheme` with edge-to-edge system bars. Screen 5 (block list) belongs to Phase 2; nothing beyond the theme was built.

- **titleMedium slot (Phase 0, verifier finding).** `NocturneTypography` initially defined 14 of M3's 15 slots; `titleMedium` fell through to the Material default (Roboto, 16sp/24sp/0.2sp tracking). Now mapped to the h5 heading style (16px, weight 500, lh 1.12, −0.015em) — the same metrics as `titleLarge`, since Nocturne has fewer distinct sizes than M3 has slots. All 15 slots now use Inter with chosen metrics.
- **M3 inverse / error / scrim roles (Phase 0, verifier finding).** `darkColorScheme` initially left `inversePrimary`, `inverseSurface`, `inverseOnSurface`, `error`, `onError`, `errorContainer`, `onErrorContainer` and `scrim` at Material defaults, leaking Roboto-era palette colours into the canonical theme. Mappings:
  - Inverse roles (snackbars/toasts) take the neutral ramp's light end — `inverseSurface` = neutral-200, `inverseOnSurface` = neutral-900 (M3's tone-90/20 pairing), `inversePrimary` = accent-700 (a deep step, legible on the light inverse surface).
  - `scrim` = neutral-900 at 50% (`0x80292B31`) — the value the CSS `.dialog-backdrop` already authors, replacing M3's pure black.
  - **Error family — approved by owner on 9 September 2026.** Nocturne names no error colour, so one was derived using the system's own construction: OKLCH on the shared lightness scale, hue 25 (warm red — the hue of the mocks' `#8B0000` typo underlines), chroma in the accent's range. `error` = `#d4716b` (L 0.660, C 0.125 — the accent's own L/C), `errorContainer` = `#612421` (mirrors the accent-800 step), `onErrorContainer` = `#ffebe8` (mirrors accent-100), `onError` = bg (same convention as `onPrimary`). If the owner prefers a different red, it is a four-value change in `Color.kt` only.
- **Shadow approximation — carry-forward caveat (Phase 0, verifier note).** The elevation translation (edge + blur÷2 + alpha) preserves token colours and alphas but not the CSS Y offsets (6px/16px) or 1px edge width. Before any later phase relies on the approximation across screens, the first consuming card and dialog must be compared against their renders (screens 12 and 14 first).

- **Phase 0 closed (9 September 2026).** Owner approved error #d4716b, errorContainer #612421, onErrorContainer #ffebe8, and onError = bg. Both review findings are resolved and all five acceptance checks passed for 221ae96. Phase 1 data-layer implementation may proceed; shadow visual comparison remains a later UI checkpoint.

## Phase 1 — Data layer

- **Schema is normalized, not JSON blobs (Phase 1).** Apps and sites are their own tables (`blocked_apps`, `blocked_sites`) with a **global UNIQUE index** on `package_name` / `domain`, rather than arrays inside the block row. Rationale: "an app/site belongs to exactly one block" (PRD §4) becomes a database constraint — a duplicate cannot be written even by a future code path that skips the repository; conflicts are detected by a lookup and surfaced as `AddTargetResult.Conflict(holdingBlockId, holdingBlockName)`; moving is a single atomic `UPDATE … SET block_id`. Constrains later phases: the block detail/editor screens must go through `BlockRepository.addApp/addSite/moveApp/moveSite`, not raw DAO inserts.
- **Storage columns are snake_case via explicit `@ColumnInfo` (Phase 1).** Room does not convert camelCase Kotlin fields to snake_case columns; every multi-word column is named explicitly. The `event` table columns match the PRD §10 schema literally: `event(id, name, timestamp_utc, block_id, target, params_json)`.
- **Events have no foreign key to blocks (Phase 1).** PRD §9/§10: Stats are all-time; events must survive block deletion, so `event.block_id` is a plain Long, not a FK. `blocks` children (apps/sites) do cascade on block delete.
- **Stats calendar semantics (Phase 1).** "This week — last 7 calendar days" = local calendar window from the start of the day 6 days ago through now (implemented as `StatsCalculator.calendarWeekStart`, passed to the query as a bound parameter — no tz logic in SQL). "Days active — days since first launch" = whole calendar days between first-launch date and today, local time; launch day itself is day 0. "Best day" groups by local calendar day in SQL (`strftime … 'localtime'`). Instrumented fixtures seed local-noon timestamps so every event lands in exactly one day bucket regardless of run time — later Stats work should keep that convention.
- **Walk-away rate denominator (Phase 1).** `walk_aways ÷ (walk_aways + challenge_completed)` per PRD §9. `challenge_abandoned` and `turnoff_completed` are excluded from the denominator (PRD §8: abandonment is not a walk-away; turn-off is a separate gate). Rate is 0.0 when there is no data, not NaN.
- **First launch lives in an `app_meta` key-value table (Phase 1).** "Days active" needs a first-launch instant that isn't tied to any event. `app_meta(key, value)` with `INSERT OR IGNORE` writes `first_launch_at` on first repository use; it is never overwritten. The instant records first *repository* use, which in Phase 1 is test-only; when UI phases start logging, that becomes first app use.
- **App labels are not stored (Phase 1).** `blocked_apps` stores `package_name` only. Labels for list/detail UIs will be resolved at display time via `PackageManager` (Phase 2), which also handles uninstalls. If that proves too slow on the list screen, a label-cache column is a migration — decided then.
- **`createBlock` forces `enabled = false` (Phase 1).** PRD §4: a new block is saved OFF regardless of draft state. The editor-level conflict resolution is expected to happen before save; if a duplicate app/site still reaches `createBlock`, the unique index fails loudly rather than duplicating.
- **KSP 1.9.24-1.0.20 + room-compiler 2.6.1 (Phase 1).** The Room annotation processor needs an annotation processor; with Kotlin 1.9.24, KSP is the pairing (kapt would also work but is slower and legacy). Version is Kotlin-locked: KSP releases are prefixed by the Kotlin version, so a Kotlin bump requires a KSP bump. Room has no schema export configured (`exportSchema = false`) — if migrations ever become needed (they shouldn't before release), turn export on and start versioning deliberately.
- **Test stack (Phase 1).** JVM unit tests cover the pure Stats formulas (`StatsCalculatorTest`, 7 tests); Room/repository behaviour is covered by 10 instrumented tests against an in-memory database on the device (`androidx.test:runner` 1.5.2, `androidx.test.ext:junit` 1.1.5, plain JUnit4 + `runBlocking` — no additional coroutine-test dependency). `EventRepository` takes an injectable `clock: () -> Long` so Stats windows are pinned exactly in tests.

- **Phase 1 verification (9 September 2026, 8ea7a33): FAIL.** Submitted acceptance checks pass (7 JVM, 10 device tests), but three additional device probes reproduce partial persistence after failed creation, case-variant domain duplicates, and website entries in the per-app leaderboard. Fix before Phase 2; see `Verification Feedback/phase-1-verification/REPORT.md`. No production code changed by verifier.

- **createBlock is one transaction (Phase 1, verifier finding).** Parent row and all child app/site inserts now run inside a single `db.withTransaction` (room-ktx); the repository takes the `TokiDatabase` instead of the bare DAO. A rejected save — a duplicate reaching the unique index, or cancellation mid-write — rolls back completely: no half-built block, no targets silently reserved. Regression test seeds a holder, forces a failure on the second child, and asserts nothing from the failed save persisted while the original block stays intact.
- **Domain identity is canonical (Phase 1, verifier finding).** Domains are case-insensitive in DNS, so the repository canonicalizes at the storage boundary: trim, strip one trailing root dot, lowercase. All paths (create, add, find, move, remove) canonicalize; the tables hold only canonical spellings, so the UNIQUE index protects the same identity the repository compares. `REDDIT.COM` now conflicts with `reddit.com`. Package names are left untouched (Android packages are case-sensitive). Canonicalization adds no path handling — whole-domain only (PRD §13).
- **Events carry `target_type` (Phase 1, verifier finding).** The per-app leaderboard must exclude websites (PRD §9), but packages and domains both contain dots — shape cannot decide. The event table gains a nullable `target_type` column (`app` | `site`, values aligned with §10's `trigger_type`); `log()` requires it whenever `target` is set (loud `require`, since a kind-less target would silently vanish from the leaderboard), and the leaderboard query filters on it. Global walk-away totals and the rate stay inclusive of both kinds. DB version bumped 1 → 2; no migration ships because no production database exists yet (nothing outside tests builds `TokiDatabase`) — the Phase 2 database provider must decide the migration story deliberately.
- **Test-quality note applied (Phase 1, verifier note).** The params round-trip check now parses `params_json` with `JSONObject` and asserts the actual key/values via JUnit assertions, replacing a bare Kotlin `assert` (which is JVM `-ea`-conditional). A `logRejectsTargetWithoutType` test pins the new `require` contract. Suite after fixes: 7 JVM + 14 instrumented, all passing.

- **Phase 1 closed (9 September 2026, a78f877).** Independent re-verification PASS: all three blockers resolved; fresh run passed 7 JVM and 14 device tests with no failures. GLM may begin Phase 2, block list and create flow. Short record: `Verification Feedback/phase-1-reverification/REPORT.md`.

## Phase 2 — Block list and create flow

- **Hand-rolled navigation (Phase 2).** A sealed-route back stack in `MainActivity` with `BackHandler`; no `androidx.navigation` dependency (rule 8: no new dependencies without asking — five routes don't justify one). New routes push; back pops; the create flow keeps its own step state.
- **Phosphor icons as a bundled glyph font (Phase 2).** `Phosphor-Regular.ttf` (v2.1.1) is bundled in `res/font` and glyphs render as text by codepoint (`ui/icons/Phosphor.kt`, constants extracted from the official CSS). No icon dependency added; codepoints are compile-time constants so a glyph typo fails visibly in review, not silently.
- **Database provider (Phase 2).** `TokiApplication` owns the Room database lazily, with `fallbackToDestructiveMigration()`: no builds leave this device yet, so a dev-phase schema bump rebuilds instead of crashing a stale install. **Revisit before any distribution.**
- **One UI dialog freeze — record kept for future phases (Phase 2).** Raising a Compose Dialog while the soft keyboard is up and focused on this S23 Ultra / One UI build wedged the process's frame pipeline in testing: composition completed, no frame was ever scheduled, the UI froze (main thread idle in epoll, no ANR, no crash). `focusManager.clearFocus(force = true)` before raising a modal reliably retracted the keyboard and unblocked rendering. The conflict flow this fix served was later removed entirely (see the ownership decision below); the finding stands as guidance: **any future modal raised from a text-field context must clear focus first, and must be device-tested with the keyboard both up and down.**
- **Record correction — the shipped conflict sheet was not a Dialog (Phase 2, verifier finding).** The committed implementation at 8f1ad1e used an in-place `Box` overlay, not the `Dialog` window that entry claimed, and its backdrop did not intercept input (taps passed through to the editor underneath). The claim above was wrong and is superseded by the owner decision below, which removed the conflict flow entirely rather than repairing it. Scrim colour `0x8C0D0E16` was the mock HTML's backdrop value (#0d0e16 at 55%) — a mock-scene value, not a styles.css token; the hex grep (which requires a `#` prefix) stays clean.
- **Conflict resolution is deferred to save (Phase 2).** The editor adds a *moved* target to its draft; the reassignment happens inside the `createBlock`/`updateBlock` transaction (repository now moves targets held elsewhere instead of failing). Abandoning the flow after choosing *Move it here* leaves the old block untouched. `createBlock` normalizes its draft (in-draft duplicates collapse); the unique index remains the storage backstop.
- **Repository grew editor APIs (Phase 2).** `appHoldingBlock`/`siteHoldingBlock` (for the dialog), `updateBlock(id, draft)` (transactional field + target-list sync). The raw `updateBlock(Block)` from Phase 1 was replaced. Instrumented tests updated: the Phase 1 rollback regression became a normalization/move test (a rejected save is no longer reachable through the API), plus a full edit-sync test.
- **Typing-cost estimate is 0.3 s/char (Phase 2).** The acceptance-pinned point (100 chars ≈ 30 s) fixes the rate; `formatEstimate` renders minutes above 60 s. The PRD's prose "300 around two and a half minutes" is inconsistent with its own 20-wpm basis — the tested constant wins (300 → ~1 min 30 sec). Change `SECONDS_PER_CHAR` only with the owner.
- **Edit reuses the create flow (Phase 2).** Same four steps, prefilled, appbar title "Edit block" (mock only titles the create case). Saves via `updateBlock`; `block_edited` carries `fields_changed` compared **before** the write. Create-mode telemetry (started/step/abandoned) does not fire during edits.
- **Toggle-off is ungated in Phase 2 (Phase 2).** Turning OFF via the list/detail toggle happens immediately and logs `block_turned_off`. The typing gate (screen 22) is Phase 5 per the phase plan; until then turning a block off is frictionless. Toggle ON always routes to the turn-on confirmation.
- **App picker (Phase 2).** Manifest `<queries>` with MAIN/LAUNCHER (no `QUERY_ALL_PACKAGES`); Toki Shrine excluded by package; labels resolved at display time via `PackageManager` with package-name fallback for uninstalls. Search matches label or package, case-insensitive, with match count.
- **Name step validation (Phase 2).** Next is disabled while the name is blank — minimal guard against a degenerate nameless block; not in the mock but clearly intended. Step 1 Next stays enabled even with zero targets (mock-faithful; a block that covers nothing simply blocks nothing).
- **Stats / Settings / Share feedback are inert (Phase 2).** The home-screen controls exist per screen 6 but their destinations are Phase 3 (settings) and Phase 7 (stats, feedback); they navigate nowhere until then.
- **The instrumented-test harness resets app data (Phase 2).** After every `connectedDebugAndroidTest` run the device app is gone (AGP uninstalls both APKs), so any manually created fixture blocks disappear on next launch. Restore pattern that worked: checkpoint the DB locally (`PRAGMA wal_checkpoint`), `adb push` + `run-as cp` back into `databases/`. Keep this in mind when manually verifying against seeded data.
- **Visual conformance (Phase 2).** Judge pass vs `design/screens` renders: 11/11 pairs after two repairs (conflict-sheet grammar "An app", body as a single annotated paragraph). The conflict sheet has since been removed by the ownership decision below; the conformance result covers the remaining screens. Shadow carry-forward: the first card/dialog consumers still owe a render comparison when Phase 2+ UI reintroduces them.
