Implementation: `app/src/main/java/com/arjunrana/tokishrine/data/stats/`. ## Public API for GLM

- `TokiApplication.statsRepository.state: StateFlow<StatsScreenState>`: Loading, NoUsageAccess, NoBlocks, Ready(dashboard), Error(message). NoBlocks (S6) only when there is no enabled block **and** no counted outcome in the seven-day window (P7-F10); otherwise Ready with `blocksOn == false` for the "No blocks are on" note. Collect in the Stats screen. `suspend refresh()` rechecks permission and reads data off the main thread; call on entry/resume and after permission return. Existing MainActivity resume and accessibility-service ingestion are already wired; avoid duplicate long-lived polling.
- `suspend recalibrate(): Boolean`: invoke once after confirmation, disable repeat taps while running; false means replacement failed. Repository owns `baseline_recalibrated`; UI must not emit it again.
- `suspend setVisitOverride(packageName, minutes): Boolean` / `suspend clearVisitOverride(packageName): Boolean` (P7-F6 sheet Save / "Use measured"): whole minutes `StatsLedger.OVERRIDE_MINUTES_MIN..MAX` (1..120, provisional), invalid input throws `IllegalArgumentException`; the repository refreshes `state` after a successful write; false means nothing changed. No event is logged.
- `StatsDashboard`: seven chronological `days`, week saved sum and `savedPerDayMs` (Avg time saved = 7-day saved ÷ 7), week `attempts`/`nopes`/`passes`/`nopeRatePercent` (the card shows only "N%", 9 October addendum), **today since local midnight**: `todaySavedMs`, `todayAttempts` (counted nopes + push-throughs; one counted nope adds exactly 1), `todayNopes`, `todayNopeRatePercent`, nullable `todayScreenMs` ("Screen time X today"; null unless history covers midnight→now), app rows, nullable spent total, unmeasured pass count, baseline capture timestamp, usage availability, `blocksOn`. The "vs your usual" comparison and the old Attempts/day tile are removed with their fields (`screenDailyMs` still exists in the persisted `stats_state`, unused by the screen; the dashboard's `attemptsPerDay` field is gone, P7-F13). Raw durations are milliseconds. Dates are `LocalDate`, not a fixed Monday–Sunday order.
- `StatsDurationFormat.duration(ms)` and `.visitMinutes(ms)` own rounding. If `attempts == 0` (or `todayAttempts == 0` for today's rate), render rate as “—” despite the internal safe numeric rate of 0. Screen percent 0 is hidden. Null means unknown: never coerce it to zero. Chart bar value labels (`statsBarSpecs` in presentation) render whole minutes in every range (`140m`, never `2h 12m`) per the 4 October §17 addendum; hours+minutes applies to wider figures only.
- `StatsApp` supplies package, nopes, saved duration, effective `usualVisitMs` (override when set, else measured), `measuredVisitMs` + `usesFallback` (measured baseline; "Use measured (Xm)"), nullable `userVisitMs` (the chip never marks a user-set value, 9 October addendum) and `savedWith(visitMs)` for the sheet's live "N nopes × Xm" line. Resolve labels through existing InstalledAppsRepository; sort equal saved durations by display label (no icons/taps). The underlying list is installed packages that are app targets of enabled blocks, supported browsers while an enabled block has a site (site savings attribute to the browser), **and any package with a counted outcome this week** even if its block is off or it left the block (P7-F10; uninstalled packages stay excluded). Without an override, old savings can differ from nopes × current baseline after recalibration; do not recalculate them in UI.
- `StatsDay.spentMs` / dashboard spent total is null if any contributing push-through lacks measurement. Show “—” and “Some visits couldn't be measured” when applicable. A day without passes returns 0. `usageAvailable == false` calls for a neutral “Usage data isn't available right now” message; saved/outcome metrics remain available if permission is still granted.
- Permission wiring: add `USAGE_ACCESS` to AppPermission, Settings/checklist and request dispatch; use AndroidUsageSource.hasAccess and ACTION_USAGE_ACCESS_SETTINGS. Five-row progress; Better experience group. Keep Accessibility-only activation gate. Manifest declaration already exists. Lifecycle result handling should log the grant transition once, including Stats CTA grants.
- Local interaction events already have constants/taxonomy: stats_viewed(state), stats_info_opened(which), stats_usage_access_cta_tapped, usage_access_granted, stats_recalibrate_tapped. Log entry once after resolved state (not each flow emission), using existing accepted entry/recreation conventions. No event on initial baseline capture beyond permission grant; recalibration success belongs to repository.

## Durable accounting / migration (Codex-owned)

Room v4 adds stats_state, stats_baseline, stats_outcome, stats_usage_event, stats_coverage. Explicit MIGRATION_3_4 creates only these tables/indexes; leaves all v3 tables/rows untouched. No destructive fallback or historical outcome backfill. Exported v3 and v4 schemas are retained.

ChallengeRepository writes raw terminal event + StatsLedger + idempotency marker in the same transaction. CompletionRequest carries the original target/type plus `hostPackage`. Pause successes and explicit nopes enter the ledger under `StatsLedger.statsPackage`: the target package for an app interruption, the **hosting browser package** for a site interruption (4 October §17 addendum). DetectionEngine stamps `DetectionTrigger.hostPackage` (the settled browser window's package), the service passes it as `BlockActivity.EXTRA_HOST_PACKAGE`, and ChallengeConfig carries it into WalkAway/CompletionRequest. A site outcome without a host package records nothing (never the domain). Raw walk_away/challenge_completed events keep the domain target and unchanged payloads. Site and app outcomes on one browser therefore share its outcome rows, savings, attempts, first-browser-visit spent measurement and single dedup sequence. No backfill: pre-change site outcomes were never written. Stable session ID is the primary key. Turn-off paths and absences under 15 s do not write outcomes; a pause auto-nope after 15 s away (`walk_away` source `auto_away`, P7-F3) is an ordinary nope outcome. Raw walk-away counter remains inclusive and undeduped. Leaderboard source (`StatsRepository.leaderboardPackages`): installed app targets of enabled blocks plus, while any enabled block has a site, every installed supported browser from the bundled detection config (zero rows included), plus packages with a counted outcome in the window (P7-F10).

**v5 (P7-F6, 8 October addendum).** `stats_visit_override(packageName PK, visitMs, setAt)` holds the user's usual visit length per app. Explicit `MIGRATION_4_5` only creates this table; every v4 table/row is untouched; v3, v4 and v5 schemas are exported. An override **re-values that app's counted nopes for the week shown** (week totals, days/chart, today, app row); ignored (deduped) nopes stay 0. Stored `savedMs` is never rewritten, the ledger keeps freezing the measured baseline at resolution, and clearing the override restores those frozen values. Overrides survive Recalibrate and revocation. Apps without an override keep frozen per-outcome values.

The last counted package outcome (durable insertion order) controls the fixed nope window (`StatsLedger.DEDUP_MS`, two minutes since the owner change of 10 October 2026; five before). Outcomes keep the `counted` flag frozen at resolution, so the change never rewrites earlier rows; ignored rows never reset it. Passes break the sequence. Saved duration and baseline ID are frozen in each row. Before first baseline capture, fallback savings are recorded with null baseline ID and stay immutable. Dates are saved at resolution. No FK cascades remove historical stats with a block. Baseline replacement is atomic with its success event; historical outcome values are untouched.

## Usage reconstruction and conservative limits

Android raw events are retained only a few days, not guaranteed seven. Activity callbacks are not public app-launch counts. We use available complete foreground visits, not expanded aggregate bucket durations divided by resume callbacks. Official references: [UsageStatsManager](https://developer.android.com/reference/android/app/usage/UsageStatsManager), [UsageEvents.Event](https://developer.android.com/reference/android/app/usage/UsageEvents.Event).

- **Usual visit length (P7-F6):** at initial capture/Recalibrate, per package, ignore completed visits shorter than `AppConfig.MIN_VISIT_MS` (30 s), then take the `AppConfig.VISIT_PERCENTILE` (75th) percentile by linear interpolation between closest ranks; fewer than `AppConfig.MIN_VISITS` (3) qualifying visits → `StatsLedger.FALLBACK_MS` (10 m). The three usual-visit constants live in the shared config file (P7-F11). `samples` stores the qualifying count. **Existing installs (Arjun, 8 October): no one-time recompute** — baselines stored before v5 keep their old mean until the next Recalibrate (which re-measures only the last 7 days of Android history, not pre-install time).
- Read recent seven days initially/recalibrating, then incrementally with a one-minute overlap. After more than a day without ingestion, query recent history anew and begin coverage at the first returned event. Null/unlocked-state failure is unavailable. Duplicate events are ignored by deterministic key. Keep at most eight days of raw usage events during ingestion; retain outcomes/baselines. Revocation hides the dashboard and retains data; regrant does not replace the baseline.
- Coverage spans merge only when overlapping; reconstruction runs separately per span. Do not bridge a lost-history interval. Android cannot prove an OEM's event stream is exhaustive; device validation remains required.
- RESUME opens a foreground segment, PAUSE closes the matching package/activity, another RESUME transfers ownership. Lock/screen-off/shutdown/startup closes and breaks visits. Ignore duplicate resumes/orphan pauses. Merge adjacent different-activity segments of the same package only within one second; preserve actual segment durations (exclude the transition gap). This is a conservative reconstructed visit, not an authoritative OS launch count. Multi-window uses one foreground owner to prevent double-counting; work profiles are out of scope.
- A still-open activity tail can contribute observed screen time up to the successful read boundary, but not a completed visit baseline or post-challenge measurement. Completed visits wait two seconds for adjacent activity transitions before attribution. Initial history uses capture-time zone because Android supplies no historical timezone; cached events keep their first-ingested zone. Outcome dates never rebucket.
- Post-challenge candidate must be the first non-Toki completed visit starting at/after success, to the exact target, within **30 seconds** of completion, with covered history through its end. This is a conservative attribution guard, not a new timeout on the challenge or pause. If an unrelated app is first, return is late, history is missing or the visit remains open, leave spent unknown. One visit can belong to at most one success; claimed measurements never reassign. No measurement of every app unlocked by the pause. Store the visit duration on the completion date even across midnight.
- All-app screen average is displayed only with coverage of all seven dates through now; otherwise null. Overall baseline uses complete available local days and can be null. Saved/attempt metrics still divide by seven as specified. OS-retention limits never become fabricated screen-time zeros.
- MainActivity refreshes on resume. Existing accessibility service ingests once a minute while alive; no additional service, alarm, network, wake lock or dependency. Process death or OEM shutdown may lose history beyond platform retention; expose unknown instead of inventing time. Blocking does not query Usage Access.
